## What to build

Execução dos cenários do fluxo crítico de negócio: Rascunho → Fechamento → Estoque, com todas as validações de quantidade.

**Objective:** provar o invariante central — o último envio do dia vira o Estoque — e as regras de validação de quantidade por Unidade de medida.
**Scope:** `/fechamento`, `/estoque`; `salvarRascunhoAction`, `enviarFechamentoAction`.
**Preconditions:** QA-02; login como Dono e como `operador.centro` (QA-04 pode prover; senão criar mínimo necessário).
**Identity / Role:** Operador com `submit_fechamento`; Dono.
**Data requirements:** Produtos ativos de seed (kg, L, unidade) para cobrir decimais × inteiro.
**Tools:** Playwright; verificação de estado via UI de `/estoque` e `/dashboard`.
**Execution steps:** abrir Fechamento (Rascunho lista todos os ativos); salvar Rascunho parcial → refresh → valores persistem; enviar completo → Estoque reflete exatamente; tentar enviar com campo vazio → erro "todos os Produtos ativos"; negativo → erro; 100.000 → erro de teto; 99.999 → aceito; 1,5 em `unidade` → erro "inteiro"; 0,001 em `kg` → aceito; 0 → aceito; sem Produtos ativos → erro específico.
**Expected behaviour:** conforme `quantities.ts` (teto 99.999, ≥0, decimais por unidade) e `app.enviar` (todos os ativos obrigatórios; Estoque substituído).
**Evidence required:** screenshots antes/depois, mensagens de erro exatas, estado do Estoque por Produto.
**Do not do:** não corrigir mensagens confusas — registrar como achado; não pular o caso "0" (é quantidade legítima).

## Acceptance criteria

- [ ] Happy path Rascunho→Fechamento→Estoque verde com evidência
- [ ] Todas as fronteiras de quantidade executadas (0, negativo, 99.999, 100.000, decimal por unidade)
- [ ] Envio incompleto rejeitado com mensagem clara
- [ ] Estoque pós-envio confere item a item com o enviado
