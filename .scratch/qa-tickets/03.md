## What to build

Execução dos cenários de autenticação e sessão da matriz, com evidência por cenário (PASS/FAIL/BLOCKED/SUSPICIOUS).

**Objective:** provar que login, logout, rate limit, sessão inválida/expirada e redirects se comportam como especificado.
**Scope:** `/entrar`, `entrarAction`, `sairAction`, middleware, layout `(app)`, cookie `doguinho_session`.
**Preconditions:** QA-02; dev server limpo (rate limit zerado).
**Identity / Role:** Dono de seed; anônimo.
**Tools:** Playwright (contexts isolados), inspeção de cookie, network.
**Execution steps:** login feliz → redirect `/fechamento`; senha errada → mensagem genérica; e-mail inexistente → **mesma** mensagem; 6ª tentativa → bloqueio de rate limit; logout → cookie removido + redirect; cookie adulterado → redirect `/entrar`; acesso a `/entrar` logado → redirect `/fechamento`; URL interna deslogado → redirect `/entrar`.
**Expected behaviour:** conforme `app.ts`/`actions.ts`/`middleware.ts` (mensagem única, 5 tentativas/15min, TTL 12h).
**Evidence required:** screenshots, respostas de rede, estado do cookie por cenário.
**Do not do:** não reiniciar o server no meio de um cenário de rate limit (reset documentado só entre cenários); não testar força bruta além do limite especificado.

## Acceptance criteria

- [ ] Todos os cenários de auth da matriz executados com veredito e evidência
- [ ] Mensagem de falha idêntica para e-mail inexistente e senha errada (comparada)
- [ ] Rate limit bloqueia a 6ª tentativa e permite após reset de ambiente
- [ ] Sessão inválida/adulterada redireciona em página protegida
