## What to build

Matriz de testes completa (`docs/qa/QA_PLAN.md`): para cada fluxo do `QA_MAP.md`, cenários com ID, prioridade, identidade/role, precondições, dados, passos e resultado esperado.

**Objective:** transformar o mapa da aplicação em cenários executáveis.
**Scope:** todos os fluxos mapeados; técnicas: happy path, inputs inválidos, fronteiras (0/1/negativo/99.999/100.000/decimais por unidade/texto longo/unicode), estados (loading/vazio/rascunho/enviado/erro), navegação (refresh/back/forward/URL direta/deep link/nova aba), interação (duplo clique/duplo submit/submit durante loading), persistência (create→refresh, logout→login), autenticação (deslogado/expirada/inválida), autorização (role errada/URL direta/ação escondida), boundary de Loja (Vínculo), erros de rede quando simulável, UI (desktop/mobile/overflow/lista vazia).
**Preconditions:** QA-01 concluído.
**Identity / Role:** matriz referencia as identidades de `docs/qa/TEST_IDENTITIES.md`.
**Tools:** editor + conhecimento do código (validações em `quantities.ts`, `app.ts`).
**Expected behaviour:** cada fluxo tem ≥1 cenário happy path + inválido + fronteira + autorização; todo cenário tem resultado esperado objetivo.
**Evidence required:** `docs/qa/QA_PLAN.md` com tabela de cenários (ID, área, role, precondição, passos, esperado, técnica).
**Do not do:** não executar os cenários aqui (é QA-03+); não inventar fluxos ausentes do QA_MAP sem marcá-los como "não encontrado na UI".

## Acceptance criteria

- [ ] Todo fluxo do QA_MAP tem cenários nas técnicas aplicáveis
- [ ] Cada cenário tem ID único, role, precondições e resultado esperado
- [ ] Cenários de boundary usam as regras reais de `quantities.ts` (teto 99.999, decimais por unidade)
- [ ] Cenários de autorização cobrem as 7 permissões e o Vínculo
