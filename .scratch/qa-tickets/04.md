## What to build

Execução dos cenários de autorização: criação das identidades de QA via UI e verificação de permissões, ações escondidas, URL direta e boundary de Loja (Vínculo).

**Objective:** provar que Perfil + Vínculo limitam o que cada usuário vê e faz — na UI e no servidor.
**Scope:** `/usuarios`, `/perfis`, `/fechamento`, `/estoque`, `/historico`, `/dashboard`, `/produtos`, `/configuracoes`; param `?loja=`; ações por permissão.
**Preconditions:** QA-02; login como Dono.
**Identity / Role:** Dono cria `operador.centro` (Vínculo: Centro), `operador.multi` (Centro + Jardim Juliana), `restrito` (Perfil custom só `read_estoque`, Vínculo: Centro).
**Tools:** Playwright com contexts paralelos (Dono + operadores), múltiplas abas.
**Execution steps:** criar Perfil "Restrito" (só `read_estoque`) e os 3 usuários via UI; como `operador.centro`: ver só Centro em todas as páginas; `?loja=<id-de-outra>` → fallback seguro; como `restrito`: não ver ações de submit/gerenciamento; tentar URL direta de páginas proibidas; como `operador.multi`: operar as 2 Lojas e não ver Magalhães.
**Expected behaviour:** enforcement visível na UI **e** erro de autorização no servidor quando a ação é forçada (camada app rejeita).
**Evidence required:** screenshots por role, respostas de rede de ações negadas, tabela role × página × ação.
**Do not do:** não editar código para "fazer passar"; não usar a conta Dono para validar visão de operador.

## Acceptance criteria

- [ ] 3 identidades criadas via UI (o próprio fluxo de criação é veredito de QA-08)
- [ ] Boundary de Loja verificado em dashboard/estoque/histórico/fechamento
- [ ] `?loja=` fora do Vínculo cai em fallback, nunca na Loja alheia
- [ ] Ação proibida forçada (sem UI) é rejeitada pelo servidor com evidência
